# Arm64: design

Windows, 5.0 spec 7 (the frame is `2026-11-17-windows-5-0-umbrella.md`). Brainstormed with the owner on
2026-11-19 and approved. Decisions are on the dashboard under Sanduhr für Claude (Windows).

## The goal

A Windows PC with an Arm processor gets a native Sanduhr from both places it is distributed: the Microsoft
Store and the GitHub installer. Today both ship x64 only, and an Arm PC runs it through Windows' emulation.

**Success:** the 5.0.0.0 Store submission carries an x64 and an arm64 package; the 5.0.0.0 GitHub release
carries an x64 and an arm64 installer, each with its own update feed; an arm64 install updates itself from
the arm64 feed and an x64 install keeps updating from the feed it reads today; and an x64 GitHub install
running on an Arm PC says once that a native build exists. Nobody on the team owns Arm hardware, so every
check runs on GitHub's `windows-11-arm` runner.

## Out of scope

- **Arm hardware testing.** No one has a device. Section 8 lists what that leaves unseen.
- **Switching an install from x64 to arm64 from inside the app.** Velopack can change an install's channel,
  and that would turn the notice's link into a button. Not tried, so not in 5.0.
- **An in-app test of the update path against a private feed.** It would need a way to point the updater
  somewhere other than GitHub, which is a way to redirect updates. Not worth the risk.
- **Upgrading `vpk` or the Velopack library.** The trial used the installed versions; a newer `vpk` exists.
- **The Mac and the VS Code extension.**
- **The move of the Windows download links from `releases?q=v4` to `releases?q=v5`.** That is a 5.0 release
  task, and the release workflow already refuses a tag whose major the links do not match.

## 1. What was checked (2026-11-19)

A trial build in a scratch folder, from an x64 PC, with the commands the build scripts already use plus
`-r win-arm64`, then `vpk pack --runtime win-arm64 --channel win-arm64`. Nothing was uploaded.

- **The app cross-builds.** 499 files. `Sanduhr.exe`, `mcp\sanduhr-mcp.exe` (14.4 MB, trimmed),
  `WebView2Loader.dll`, `coreclr.dll` and the WPF native libraries are arm64. Of 486 `.dll` and `.exe`
  files, 166 are arm64, 320 are architecture-neutral managed code (all 99 that are not resource files have
  a CLR header), and none is x64.
- **Velopack keeps the architectures apart by channel.** Every arm64 output carries `win-arm64` in its
  name: `626Labs.Sanduhr-win-arm64-Setup.exe`, `626Labs.Sanduhr-<v>-win-arm64-full.nupkg`,
  `626Labs.Sanduhr-win-arm64-Portable.zip`, `releases.win-arm64.json`, `assets.win-arm64.json`,
  `RELEASES-win-arm64`. None collides with an x64 name. The package's nuspec records
  `<channel>win-arm64</channel>` and `<machineArchitecture>arm64</machineArchitecture>`.
- **An install follows the channel it was packaged with.** Velopack's default channel is the one in the
  installed package, so `UpdateChecker` needs no change: it passes no channel today and must keep passing
  none.
- **Velopack's helper programs are x86 in the arm64 package** (the Setup stub, `Update.exe`, the execution
  stub). They are the same programs an x64 install has run since 3.8.
- **A wrong restore ships an untrimmed MCP server.** The first trial run failed the 30 MB gate with a
  79.4 MB server: the MCP project's restore had been rewritten mid-build without the runtime, so the trim
  step was the SDK's empty stub. An editor's automatic restore is the suspected cause. A clean restore fixed
  it. Section 2 closes the gap.
- **Native calls.** Every interop struct is sequential with pointer-sized fields and no fixed offsets. Two
  libraries are called in ways worth proving on Arm: `uxtheme` by ordinal (`#135`, `#136`) and
  `winsqlite3`. The WebView2 package ships a `win-arm64` loader.
- **The precedent.** RoRoRo ships x64 and arm64 Store packages from one submission, built by a script that
  takes the runtime, with a `windows-11-arm` CI job. Its GitHub installer is x64 only, so the second update
  feed is new ground for the estate.

## 2. The build

**`scripts/build-msix.ps1`**

- `-Runtime` accepts `win-x64` (the default) or `win-arm64` and nothing else.
- The staged manifest gets `ProcessorArchitecture` set from the runtime, next to the version it already
  sets. The committed manifest stays `x64` and is never rewritten.
- The output name carries the architecture: `dist\Sanduhr-Store-x64-v<v>.msix` and
  `dist\Sanduhr-Store-arm64-v<v>.msix` (the sideload flavor the same way). **This renames the x64 file**,
  so the release workflow, the runbook and the Store Listing Console's package list change with it.
- The publish folder is per architecture: `dist\publish` for x64, as today, and `dist\publish-arm64`.

**`scripts/build-velopack-release.ps1`**

- `-Runtime` accepts the same two values.
- **arm64 packs with `--runtime win-arm64 --channel win-arm64`. x64 passes neither**, so the x64 pack
  command stays exactly as it is today and x64 stays on Velopack's default channel, `win`. Every x64 install
  in the wild reads `releases.win.json`; an x64 build packed with any other channel orphans all of them. A
  test pins this (section 7). (Amended while planning: the runtime was first to be passed for both. Naming
  it for x64 could change what the x64 package declares about itself, and Arm PCs already on the x64 build
  update from that package.)
- The publish folder is per architecture: `dist\publish-velopack` and `dist\publish-velopack-arm64`.
- Both architectures pack into the one `dist\release` folder. Cleaning removes only the files of the
  channel being built (names containing `win-arm64` for arm64, every other file for x64), so building the
  second architecture cannot delete the first.
- The first arm64 release ships a full package only; there is no earlier arm64 package to diff against.
  From the second on, the prior arm64 package is pulled with `vpk download github --channel win-arm64`.

**The MCP server's publish (`Sanduhr.App.csproj`, target `PublishMcpServer`)**

The app's publish restores the MCP project for its own runtime, so it no longer depends on a restore some
other process may have overwritten. It does so twice, because two things read that restore: once before
the app builds the server as a project reference, and once right before the nested publish. (Measured
while planning: a restore only before the nested publish still fails with `NETSDK1047`, in the reference
build, which comes first.) The 30 MB gate stays, and its message names the cause. `Sanduhr.Mcp.csproj`
does not change, and neither does `TrustBoundaryTests`.

**The architecture gate (`scripts/check-architecture.ps1`, new)**

Given a folder and a runtime, it reads the CPU field of every `.dll` and `.exe` and fails when
`Sanduhr.exe` or `mcp\sanduhr-mcp.exe` is not the target architecture, or when any file is built for the
other 64-bit architecture. Managed, architecture-neutral files pass. Both build scripts run it after
publishing, so a wrong binary stops the build on the PC that made it.

## 3. The update feed

One GitHub release carries both feeds. An x64 install asks for `releases.win.json` and an arm64 install for
`releases.win-arm64.json`; `GithubSource` picks the newest release that has the feed asked for, so releases
before 5.0 simply have nothing for an arm64 install. `UpdateChecker` is not edited.

## 4. CI and the release checks

**Every pull request (`windows-dotnet-ci.yml`).** A second job on `windows-11-arm`:

1. Restore, build and run all three test suites natively.
2. Publish the app for `win-arm64`, then run the architecture gate, `smoke-mcp.ps1` against the published
   server, and the launch check.

**The launch check (`scripts/smoke-launch.ps1`, new).** Starts `Sanduhr.exe --demo`, waits for a visible
window, holds 15 seconds, fails if the process exits or never shows a window, then closes it. The x64 job
runs it too, so the check is proven on a runner whose result can be compared with a PC.

**The release workflow (`windows-dotnet-release.yml`).** A job on `windows-11-arm` runs the three suites as
a gate. The release job needs it, builds both Store packages and attaches both to the draft.

**The Arm check (`windows-dotnet-arm-check.yml`, new, run by hand).** The arm64 files a release ships are
built on x64 machines, which cannot run them. This workflow runs the shipped files on Arm before the release
is published. Given a tag, on `windows-11-arm` it downloads the draft release's files and:

1. Fails unless the draft holds everything: both Store packages, both installers, both full packages, both
   feeds.
2. Unpacks the arm64 Store package and runs the architecture gate, the MCP smoke and the launch check on
   its contents.
3. Installs the x64 installer silently and launches it, which is an x64 Sanduhr running emulated on Arm:
   the notice in section 5 must record that it was due.
4. Puts a marker file in each data folder, then runs the arm64 installer over the x64 install. The
   installed `Sanduhr.exe` must be arm64, the installed package's channel must be `win-arm64`, the markers
   must survive, and the MCP smoke and launch check must pass on the installed copy.

On a pull request that touches the installer path (the Velopack script, the install check, the workflow
itself), it instead builds both installers on the runner at a test version and runs steps 3 and 4. So the
switch from x64 to arm64 is exercised while this part is being built and whenever that path changes, not
for the first time on release day. (Amended while planning: this was first a run by hand with no tag, but
a workflow can only be run by hand once it is on the default branch.) The draft half is rehearsed once
after the merge, on a throwaway draft at a version below every shipped one.

## 5. The notice

An Arm user who installed from GitHub before 5.0 has the x64 build, and it will keep updating from the x64
feed forever. Nothing else would tell them.

- **When it is due:** the process is x64, the machine is Arm64, and this copy is not the Store package. The
  Store needs no notice: it hands an Arm device the arm64 package at its next update.
- **How the machine is read:** `IsWow64Process2`, which reports the machine's real architecture to an
  emulated process. The read sits in the app's interop; the decision is a pure function in Core.
- **Once, as a Windows notification** shortly after the widget is up, through the existing `Toasts` helper:

  > **A native Arm build is available**
  > This PC has an Arm processor and this copy of Sanduhr is the x64 build. The Arm build runs without
  > emulation.
  > [Get the Arm build] [Not now]

  A flag in `settings.json` (`arm_build_notice_shown`) is written once the notification is handed to
  Windows, so it never repeats. Reset clears it with the rest of the file.
- **A standing line in Settings, About, Updates** for as long as the condition holds, with the same link. A
  notification is easy to miss; this is where someone finds it again. It is a sentence on a page, not a
  reminder.
- **The link** opens the release list for the running major version
  (`releases?q=v<major>&expanded=true`, the major read from the running app, so it never goes stale).
  `INSTALL.md` names the file to pick.
- **No request leaves the app.** The link opens in the browser. Nothing new is stored beyond the flag, and
  the text names nothing personal, so streamer mode has nothing to hide. The privacy page does not change.

## 6. Release, Store and documents

- **`docs/release-runbook.md`.** Phase 3 builds two Store packages; the arm64 server cannot be smoked on an
  x64 PC, so the Arm check is where it runs. Phase 4 builds two Velopack sets into `dist\release`, x64
  first. Phase 6 uploads everything, runs the Arm check on the draft, and publishes only when it is green.
  Phase 7 drags both packages into the Packages page of the submission the API created. New gotcha-log
  rows: the x64 channel, the per-channel clean, the untrimmed server.
- **Store Listing Console.** `apps/sanduhr/config.toml` lists both package files.
- **Reviewer letter.** One sentence: the submission carries an x64 and an arm64 package with the same
  features and the same capabilities.
- **`INSTALL.md`, `README.md`, `docs/index.html`, `windows-dotnet/README.md`.** Requirements read x64 or
  Arm64. The GitHub section names both installers and says which PC takes which. A short paragraph covers
  an Arm PC that already has the x64 build; its wording (run the Arm installer over it, or uninstall first)
  follows what step 4 of the Arm check shows.
- **`CHANGELOG.md`.** One line under 5.0.
- **The umbrella spec.** The arm64 row gains the notice.
- **`DeskNative.cs`.** The comment that says x64 only is corrected.

## 7. Tests

- **Core:** the notice's decision, every combination of process architecture, machine architecture, Store
  or not, shown or not. The notice's copy and the link built from a version.
- **App:** the machine read agrees with the runtime's own answer in a native process (x64 on the x64
  runner, Arm64 on the Arm runner). The About line shows only when due. The flag is written once.
- **Pins on the scripts, read as text:** `build-velopack-release.ps1` passes `--channel` only for arm64;
  `UpdateChecker.cs` builds its `UpdateManager` with no channel; `build-msix.ps1` accepts exactly the two
  runtimes and stamps the architecture.
- **`check-architecture.ps1`:** run against a folder with a file of the wrong architecture, it fails.
- **On the Arm runner,** by running the existing suites natively: the `uxtheme` ordinals, `winsqlite3`, the
  hook's PowerShell tests.

## 8. Risks, and what stays unseen

- **Unseen before release:** the Desk drawn under the desktop icons, the glow, GPU and battery behaviour,
  and anything that depends on a real Arm device's drivers.
- **The first arm64 update.** 5.0 to whatever follows is the first time an arm64 install updates anywhere.
  The feed name, the channel in the package and the helper programs are all checked or already in use; the
  full path is not run. A task is filed to watch the first release after 5.0 on the Arm runner.
- **The Store's hand-off.** That the Store gives an existing Arm user the arm64 package at their next update
  is how the Store is documented to work and how RoRoRo ships. It cannot be observed from here.
- **A hosted runner may not show a window.** If so, the launch check falls back to the process staying up
  for 15 seconds and the log reporting startup complete.
- **The way back.** A Store submission without the arm64 package returns Arm users to x64. A bad arm64
  GitHub build is withdrawn by removing its files from the release; arm64 installs then find no newer feed.

**If this part threatens the release,** cut in this order: the arm64 GitHub installer together with the
notice (the Store alone ships arm64), then the whole part to 5.1, as the umbrella already allows.

## 9. Open, for the plan

- The exact silent-install flags of Velopack's Setup, and whether Setup starts the app after a silent
  install. Confirm against Velopack's documentation before step 3 of the Arm check relies on them.
- Whether the workflow's own token can download a draft release's files. If not, the Arm check takes the
  files as workflow artifacts from the release job plus an upload step.
- How step 3 of the Arm check observes that the notice was due: the settings flag, or a line in the log if
  a runner cannot show a notification.
- Whether the arm64 installer replaces an x64 install in place or asks for an uninstall first. Step 4 of
  the Arm check answers it, and `INSTALL.md` says whichever is true.
