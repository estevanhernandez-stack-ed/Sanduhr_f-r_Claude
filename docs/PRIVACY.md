# Privacy Policy — Sanduhr für Claude

**Last updated:** 2026-10-11
**Publisher:** 626Labs LLC
**Contact:** [GitHub Issues](https://github.com/estevanhernandez-stack-ed/Sanduhr_f-r_Claude/issues)

## Short version

Sanduhr für Claude is a **local desktop widget**. It does not run a server, does not have a backend, does not collect analytics, does not call home, and does not send your data to 626Labs or any third party.

The only network destination it contacts is `claude.ai` — and only with the credentials you yourself paste into it — to read your own Claude subscription usage so it can show it to you.

Two opt-in exceptions, both off by default. On Windows, **the Desk's weather piece** asks Open-Meteo for a forecast once you type a city in Settings ▸ Weather: only that city name (for the place search) and the place's coordinates, rounded to about 1 km, are sent; no account, identifier or Windows location. And **Publish usage** lets you send a daily per-project token-count summary to an endpoint *you* choose, and only for the Claude Code homes you tick. Nothing about your usage comes back to us; if you want it somewhere, you send it to yourself. The 626 Labs dashboard is offered as a preset destination, one among any. Details in the table and the network section below.

### On the Mac

The table above describes the Windows app. The macOS app stores the same two credentials, `sessionKey` and the optional `cf_clearance`, which are sent only to `claude.ai`:

- **Release builds** (signed with the publisher's Developer ID): the macOS Keychain, as generic-password items under service `com.626labs.sanduhr`, readable after first unlock and trusted only to the signed Sanduhr app. An update from 2.3.1 or earlier moves the values out of the old file once, checks the Keychain holds them, then deletes the file; if that fails, the file stays and is used as before.
- **Self-built development builds**: `~/Library/Application Support/Sanduhr/credentials.json`, plaintext, mode `0600` (only your macOS user account can read it).

**Accounts (2.4.0+).** Each named account has its own pair, under the same slot names as Windows: `sessionKey:{Account}` and `cf_clearance:{Account}`. Updating from 2.3.x moves the single saved key to an account called Personal. The list of account labels and which one is active live in the app's preferences (`defaults` keys `accounts` and `activeAccount`), so showing them never touches the Keychain. Each account's usage history is its own file, `~/Library/Application Support/Sanduhr/history.{Account}.json` (the old `history.json` becomes Personal's): the meter percentages with their times, kept for 30 days (rolling, as on Windows) to draw the sparklines, and never sent anywhere. Settings → Accounts → Meter history → Off stops recording an account and offers to erase its file at once; Remove Account deletes it too. Which accounts have it off is kept in the app's preferences (`meterHistoryOff`). **Data choices (item 44).** Each account's Claude Code folder, activity, project-names and sharing choices are kept in the app's preferences (`accountData`, by account label; the linked folder as its path on this Mac), follow a rename and are deleted with Remove Account. To find Claude Code folders Sanduhr lists the `.claude` and `.claude-*` folders in your home folder and checks whether each holds a `projects` folder or a `.claude.json`. To suggest a folder for an account it reads **one field** from that folder's `.claude.json` (`oauthAccount.organizationUuid`, the organization Claude Code is signed in to; never the email, names or organization name beside it), compares it in memory with the organization the account fetches from `claude.ai` (for an account that isn't active, one extra `/organizations` request with its own key, when its Data section opens), and keeps neither: the uuid is never stored or logged. Folder paths never go into a log, `snapshot.json` or `state.yaml`; `state.yaml` shows only whether a folder is linked. Labels are the names you choose; they are shown in the app and used in those slot and file names, and **never written to a log, `snapshot.json` or the debug `state.yaml`**: the snapshot names the active account only by `account_ref`, a short hash of its label. With **Follow the account I'm using** on (off by default), Sanduhr also asks `claude.ai` for the usage of your other signed-in accounts every 15 minutes, each with its own key, the same request as for the active account; the readings stay in memory. **Live Claude Code activity (item 45).** When an account's Claude Code activity is Live only or Keep a record and a folder is linked, Sanduhr reads that folder's Claude Code session logs (`projects/…/*.jsonl`) while the account is shown, to put "+Nk" (tokens used since the last refresh) on the widget's cards. From each `assistant` line it keeps only the timestamp, the model name, the input and output token counts, the working folder and the skill name, in memory; **never message content, prompts or tool output**. Live only stores nothing: no file is written, and the working folders (project names) are neither shown nor logged in this version; `state.yaml` shows only whether the folder is read and how many usage events were counted. Not tracked (the default), or no linked folder, opens no file in it.

**The vault (item 46).** When an account's Claude Code activity is **Keep a record** and a folder is linked, Sanduhr keeps a record of that folder's Claude Code sessions on this Mac, in the Windows app's vault format: `~/Library/Application Support/Sanduhr/vault/<folder id>/`, where the folder id is 16 hex digits of a hash of the folder's path (never the path or the account label). It holds one summary row per session in monthly files (`sessions-YYYY-MM.json`: the session's id, start and end times, token totals by local day, model and skill, cache-token counts, how many lines were counted or skipped, and the project as the account chose), daily totals rebuilt from them (`rollups-YYYY-MM.json`), bookkeeping per log file keyed by a hash of its path, never a readable path (`checkpoints.json`), and the record's start date and last update (`meta.json`). **Never message content, prompts, tool output or file contents.** Project names: **Names** keeps each project's folder name (`project_name`, with 8 hex digits of a hash of its path to tell same-named projects apart), as Windows does; **Hidden** keeps `p-` and 10 hex digits of a hash of the name instead, in both fields, and never the name or the folder path (a hash, not encryption: someone holding the files who guesses a name can confirm it); **Full paths** also keeps each session's working folder (`cwd`). A change applies to sessions recorded or still running from then on; sessions already finished keep the names they were kept with until erased. The record is **kept until you erase it, unlike Claude Code's own logs**, which Claude Code deletes after about 30 days. It is written in the background at launch and after each refresh, for every account that keeps a record; Live only and Not tracked never write it. A file that can no longer be read is renamed to `….bad` with a timestamp and kept (never deleted), and the record is rebuilt from the logs still on disk. **Erase:** leaving Keep a record (or unlinking the folder while recording) asks whether to erase the record; **Erase this account's data** in Settings, Accounts, Data deletes the meter history and the record after a confirmation (Keep a record switches to Live only first, so it isn't recorded again); **Remove Account** deletes both. Erasing turns the choice off first and waits for a write in progress, so an update running at that moment can't bring the folder back. Deleting the folder by hand while Sanduhr runs is not erasing: the next update records it again unless Keep a record is off. The vault is never uploaded; the MCP server reads its daily totals only for an account that shares Meters and activity (below). Vault messages in the macOS log name the operation and an error type only, never a path, project, session or label; `state.yaml` shows only `vault: {recording, months, last_ingest_ok}`.

**The Claude Usage page (item 48).** Settings, Claude Usage shows, on this Mac only, what the live reader and the record already hold for one account: token totals by day, week, project, skill and model, and the recorded sessions. It reads only the folder and record of the account shown, and only when that account's activity is Live only or Keep a record; nothing it shows is stored anew, and project names appear exactly as kept (with Hidden, the `p-` codes, which Sanduhr cannot turn back into names; the folder path appears only in a session's details when Full paths kept it). **Export CSV…** writes the session list (session id, the Claude Code folder's name, project as shown, first and last time in UTC, tokens in scope and in total, tokens by model) to a file you choose, only when you click it; Sanduhr never exports on its own and keeps no copy. **Records on this Mac** lists every record in the vault folder, including records whose Claude Code folder is no longer linked to any account, with its size, oldest day and account, and erases any of them after a confirmation naming it (an account still keeping that record switches to Live only first). `state.yaml` shows only `usage_page: {open, tab}`.

**Per-seat meters (item 74).** Once any account has a Claude Code folder linked, Sanduhr also writes, in `~/Library/Application Support/Sanduhr/`, one `snapshot.<account_ref>.json` per linked account, holding exactly what `snapshot.json` holds (percentages, reset times, status, capture time and the `account_ref` hash; never a label, email or key; for a signed-out account, only "signed out"), and `seats.json`, owner-only, listing each linked folder's path on this Mac with its `account_ref`. The statusline, the meters mod and the MCP server read them, on this Mac only, to show each Claude Code folder its own account's meters; a folder's sessions never read another account's numbers unless you linked that folder to it. An account that isn't the one Sanduhr shows is read for this once when its folder is linked (or at launch when its last reading is old), then only while it is in use: Follow the account I'm using saw it in use (its own check every 15 minutes), or Claude Code wrote to that folder lately. For the second, Sanduhr looks at the modification times of the session logs under the linked folder's `projects` folder (whether the newest is under 10 minutes old), never their contents, and keeps nothing. The read is the same request as for the active account, every 5 minutes at most. Remove Account or unlinking deletes that account's file and its row; renaming moves its file; with no folder linked neither kind of file exists.

**Reset Sanduhr… (Settings v2, slice 5).** Settings, About, Reset Sanduhr… removes what Sanduhr keeps and what it wrote, each part with a checkbox, all checked, in this order: (1) **Sanduhr's entries in your Claude Code folders**, each undone through its record in `integrations/installs.json` exactly as Remove undoes it (the MCP server entry, the statusline, the meters mod's plugin-folder entry and its `enabledPlugins` switch, the glow hooks): Sanduhr's entries come out and everything else in each `settings.json` and `.claude.json` stays as it is (a file nobody else changed ends byte for byte as it was before Sanduhr), and once no Sanduhr entry is left in a file, the `.sanduhr-backup` beside it goes too; (2) **your accounts and keys**, by Remove Account for each (its key and cf_clearance from the Keychain and the credentials file, its history file and its preferences), and the keys saved before accounts existed; a development build clears only its own credentials file, never a release build's Keychain items, and the sheet says so; a Keychain item that can't be deleted is named (by kind, never the account) in the results, to delete in Keychain Access; (3) **history and records**: everything else in `~/Library/Application Support/Sanduhr/` (meter history, the vault, `snapshot.json`, the per-seat `snapshot.<account_ref>.json` files, `seats.json`, `mcp-access.json`, `band.json`, the hand-off files and the integration scripts), and the folder itself; (4) **Desk messages**: `messages.txt` is renamed to `messages.txt.previous` beside it, replacing an older one; (5) **your themes** (`themes/`); (6) **both preferences domains**, `com.626labs.sanduhr` and `com.626labs.sanduhr.desk`, last. A Claude Code folder you uncheck keeps Sanduhr's entries, and the scripts and records they need stay in `integrations/` so they keep working and can be removed later; so do those of a folder whose step failed, and all of them when `installs.json` can't be read (the sheet says so). Before the first step, Sanduhr stops fetching (dropping the key it holds in memory), following, the per-seat reads, the vault, the Desk, the folder watchers, the band and Sparkle's scheduled checks, and every writer of those folders does nothing until it quits; at quit it sweeps the checked parts once more. Each step's result is shown in the sheet and kept nowhere. Nothing is sent anywhere. The smoke tools' `reset --dry-run` reads the same plan and removes nothing; `state.yaml` then shows only step kinds and counts, never a path, folder or label.

**Share with your agents (item 47).** The Claude Code integration on the Mac (Settings, Integrations, or `bash mac/integrations/install.sh`; opt-in) registers the `sanduhr` MCP server with Claude Code. What it may tell Claude is chosen per account in Settings, Accounts, Data, Share with your agents, and its answers become part of that Claude conversation like any other tool result. **Off** (the default): nothing about the account, as if it weren't there. **Meters**: `get_usage` (the meter percentages, reset times and pace: in a Claude Code folder linked to the account, its own, answered with `scope: seat_account`; in a folder no account links, only while it is the account Sanduhr shows, `scope: active_account_only`) and, in `get_usage_history`, its highest meter reading per day from its meter history. **Meters and activity**: also Claude Code tokens by project (`get_local_burn_by_project`, last 1, 7 or 30 days) and by model (`get_model_usage`), read from the linked folder's session logs (the same fields as the live activity above, never content), the account's own tokens since the last refresh in `get_usage`, and with Keep a record the record's daily totals and top projects (`get_usage_history`). Project names follow the account's choice: Names gives the project's folder name; Hidden gives only the record's `p-` code, computed in memory, never the name or path; Full paths gives the working folder's path when the tool asks for paths. To name projects the server checks, as Sanduhr does, whether a working folder or a parent holds a `.git` entry (its existence only). Accounts are named by `account_ref`, never their labels. **The access file.** Sanduhr hands the choices to the server in `~/Library/Application Support/Sanduhr/mcp-access.json` (owner-only, rewritten whenever a choice, a link, the account list or the active account changes): for each account that shares something, its `account_ref`, whether it is the active one, its sharing level and its meter history file's name (`history.{Account}.json`, so it holds the label as the file name does); with Meters and activity also its project-names choice, its record's folder id (Keep a record) and the linked folder's path (Live only or Keep a record), the one path in the file, because the server must open that folder's logs. Accounts with sharing off are not listed. Without the file, or with one it can't read, the server shares nothing. The server reads `snapshot.json` (or the linked account's `snapshot.<account_ref>.json` and `seats.json`, above), the access file, the history files, record folders and log folders the file names, and Desk's messages (below); never the app's preferences, the Keychain or credentials; it makes no network request and logs nothing, and the one file it writes is a Desk message request. `publish_usage` is not on the Mac.

**Installing the integrations (item 49).** Nothing is installed until you click Install in Settings, Integrations for a Claude Code folder and confirm the sheet, which says what the MCP server may read (each account's Share with your agents choice) or what the statusline shows (the meters of the account the folder is linked to, else the active account's, under Claude Code's prompt; Claude Code shows the line to you and doesn't add it to the conversation). Sanduhr then writes, only for the folder you picked: **the MCP server**, one entry `mcpServers.sanduhr` (`type`, the python3 path, the script path) in that folder's `.claude.json`, which for the default `~/.claude` is `~/.claude.json` beside it, as Claude Code keeps it; **the statusline**, one `statusLine` entry (`type` and the command running the script) in the folder's `settings.json`. Every other byte of those files stays as it was. Before the first change a copy of the file is kept beside it as `<file>.sanduhr-backup` (it holds whatever the file held, including Claude Code's own data in `.claude.json`; it is deleted again when Remove puts the file back exactly). A statusline you had is replaced only after the sheet shows it, and kept so Remove can restore it. To undo exactly what it did, Sanduhr keeps a list of its installs in `~/Library/Application Support/Sanduhr/integrations/installs.json` (owner-only): the folder and file paths, whether it created the file or the `mcpServers` object, and the value it replaced. The scripts are copied from the app to `~/Library/Application Support/Sanduhr/integrations/<stamp>/`, with `integrations/current` pointing at the set in use; an app update adds a new set there (only where something is installed) and deletes old ones, without editing Claude Code's files. To find python3 Sanduhr checks which of the usual paths exist and runs a found python3 once to read its version; it never runs `/usr/bin/python3` when no developer tools are behind it, because that would ask to install them, and starts that install only when you click Install Command Line Tools…. Remove takes Sanduhr's entry out, restores what it replaced and, with nothing installed anywhere, deletes the scripts. To show what each folder has, the page reads its `.claude.json` and `settings.json` and looks only at those two entries. Sanduhr never runs the `claude` command, never writes to a folder you didn't pick, and logs only error types, never a path; `state.yaml` shows only `integrations: {mcp_installed, statusline_installed, meters_installed, hooks_installed}`, counts of folders.

**The meters mod (item 50).** Opt-in like the others: Settings, Integrations, Meters above the prompt, Install…, for one Claude Code folder, after a sheet saying what it shows. Sanduhr copies the mod into the same `integrations/<stamp>/` folder and adds that folder's path to `env.CLAUDE_CODE_PLUGIN_DIRS` in the chosen folder's `settings.json`, keeping any folders already listed (backup and receipt as above; Remove takes out only its own entry, and the key or `env` only if Sanduhr made them). Inside Claude Code the mod **reads only `snapshot.json`** (the percentages, reset times, status and capture time it already holds; never the account label, which the snapshot doesn't carry), or with per-seat meters `seats.json` and the linked account's `snapshot.<account_ref>.json` (below), on session start and every 30 seconds, and draws the meters above the prompt; the band is on your screen, not in the conversation, and nothing is sent to Claude. It makes no network request, calls no model, runs no command and writes no file; the only thing it keeps is a short list of which warnings and resets it has already shown as a notice, in Claude Code's own store for the mod. The optional label in its settings is yours, kept in Claude Code's settings and shown only in the band.

**The notch glow hooks (item 51).** Opt-in: Settings, Integrations, Notch glow when Claude needs you, Install…, for one Claude Code folder, after a sheet saying what is sent. Sanduhr adds one entry to each of `hooks.Notification` and `hooks.Stop` in that folder's `settings.json` (backup and receipt as above; Remove takes out only those entries, and a list or `hooks` only if Sanduhr made it). Each entry runs `/usr/bin/notifyutil -p com.626labs.sanduhr.claude-code.waiting` (or `.done`), a system notification that reaches Sanduhr only while it runs and never starts it (hooks installed by earlier versions opened `sanduhr://claude-code?event=waiting` instead; Install updates them). **The notification carries only that event, in its name**: no prompt, message, tool, project, folder, session id or anything else from Claude Code; the hook passes nothing it receives from Claude Code on. Sanduhr acts only on those two names, and accepts the link only in exactly that form and drops anything else sent to it. It does nothing with the event but decide whether to glow the notch (its switches in Settings, Notch, Glow for Claude Code, off by default), which needs the bundle id of the app in front (to skip the glow while a terminal is in front) and the times of the last glows, kept in memory only. Nothing is written, logged or sent; `state.yaml` shows only `hooks_installed` (a count of folders) and the two switches. Any app on this Mac can open a `sanduhr://` link or post those notifications, so another app could make the notch glow; that is all either can do.

**Now playing (items 53, 53b).** Off until you place it (a notch wing or the strip in Settings, Desk, Notch, or the Now playing element in Settings, Desk, Layout), and it runs only while it is placed somewhere and Desk is on. While it runs, Sanduhr reads what macOS says is playing (the title, artist, album, length, position, play state and the app playing it) to draw it on the notch and the Desk. It does so through the bundled mediaremote-adapter, which Sanduhr runs with the system's `/usr/bin/perl` as a child process that prints each change to Sanduhr; if that stops working, through the change notices Music and Spotify broadcast on the Mac. **All of it stays in memory: no title, artist or app is written to disk, a log or `state.yaml`, and nothing is sent anywhere**; no network request is made for it. The one exception is yours to make: **looks for songs from Claude (item 65c)**. With the MCP server installed, Claude can suggest a gradient and letter style for songs you play (`propose_now_playing_looks`); the server never reads what is playing, it hands Claude's looks to Sanduhr through `now-playing-looks-request.json` (owner-only, read and deleted at once) and gets the answer in `now-playing-looks-result.json` (the request's id, the status, how many looks were saved and whether Style what's playing is on). Only when you press Save (or switch on Let Claude style songs directly, off by default) are the suggested songs' artist and title, colors, letter style and mood written to `now-playing-looks.json` in `~/Library/Application Support/Sanduhr/` (owner-only); **Clear Looks…** deletes it. The look Sanduhr works out for what plays is kept in memory only. The macOS log says only which source is in use and exit codes; `state.yaml` shows only `now_playing: {enabled, placed, source, state}` (`placed` names the places, such as `wing_right` or `desk`, never what plays). Which apps you switched off is kept in the desk preferences (`nowPlayingExcluded`, bundle ids); the list of apps seen playing is kept in memory only. Play/pause, next and previous are sent to the playing app through macOS only when you click. **Ask Music and Spotify directly** (off by default) lets Sanduhr ask a running Music or Spotify for its current track with AppleScript when the fallback starts; macOS asks your permission once per app first (revocable in System Settings, Privacy & Security, Automation), and Sanduhr never launches either app or asks it anything else.

**Desk messages from Claude (item 54).** With the MCP server installed, Claude can read your Desk messages and suggest new ones. `get_desk_messages` reads `~/Library/Application Support/Desk/messages.txt` (every line, comments included) and `desk-messages-state.json`, which Sanduhr writes beside its other files (owner-only) with whether a line is pinned, the pinned line itself and the rotation; the answer becomes part of that Claude conversation. This is not behind Share with your agents: the messages are on your desktop already and hold nothing about your accounts. `propose_desk_messages` never touches your list: it writes the suggested lines and an optional note to `desk-messages-request.json` (owner-only), which Sanduhr reads and deletes at once, checks again, and answers in `desk-messages-result.json` (owner-only: the request's id, the status, the reasons for a refusal and how many lines were added or skipped, never the lines). By default nothing changes until you choose Add (or Replace) in Settings, Message; Dismiss drops the suggestion. A suggestion waits only in memory, and a request older than ten minutes is ignored. With **Let Claude change the messages directly** (off by default) Sanduhr applies a valid suggestion at once. Either way the list as it was before is kept as `messages.txt.previous` beside it, so one change is always one copy away. The notification for a suggestion shows the line count and Claude's note, only while Sanduhr's alerts are on. Message text is never logged.

**Themes from Claude (item 55).** With the MCP server installed, Claude can suggest a color theme for the widget (`propose_theme`). Nothing is read for it: the server checks the theme Claude wrote and, when it passes, writes it to `theme-request.json` in `~/Library/Application Support/Sanduhr/` (owner-only), which Sanduhr reads and deletes at once, checks again, and answers in `theme-result.json` (owner-only: the request's id, the status, the theme's file key and name, the key of the theme you used before, where it was saved, and the check's notes; that answer becomes part of the Claude conversation). By default nothing is saved until you choose Save or Save and Apply in Settings, Widget, Themes; Dismiss drops it. A suggestion waits only in memory, and a request older than ten minutes is ignored. With **Let Claude change themes directly** (off by default) Sanduhr saves a valid theme at once and applies it when Claude asks. A saved theme is an ordinary file in your themes folder (`themes/<key>.json`), deletable in Settings like any other; a theme of yours is never overwritten (a taken name gets the next free one) and the built-ins cannot be replaced. The notification for a suggestion shows the theme's name and description, only while Sanduhr's alerts are on. Theme names and descriptions are never logged.

**Kept and proposed mods (item 75).** New Mod's **From Claude** lists the mods Claude made in your Claude Code sessions by reading those sessions' `dev-mods` folders. **Keep** copies one, unchanged and read-only, into `~/Library/Application Support/Sanduhr/mods/<name>/<version>/` and records its name, version, size and the session's short id in `mods/kept.json`; **Forget** deletes both. With **Let agents propose mods** on (off by default; `mods-agents.json` tells the MCP server), Claude can send a mod's files, with the name of the Claude Code folder its session runs with (such as `.claude-personal`, never a path), through `propose_mod`: they are staged read-only under `mods/.proposed/` until you keep or dismiss them, and `mod-proposals.json` tells the server each mod's name, version and your decision, never its files. The same switch writes `mods-catalog.json` for `list_catalog`: your kept mods' names, versions and descriptions and, per Claude Code folder by its folder name, whether each is on; nothing else your folders hold. `propose_install` only asks: the folder is written when you press Turn On. Check runs Claude Code's own validator on these files, which reads them and runs none of their code. A kept or proposed mod runs only when you press **Try in a Session…** (for a proposal, once Check passed; its staged files load for that one session and it stays a proposal) or, once kept, turn it on in a Claude Code folder, which writes that folder's `settings.json` by receipt (`mods/installs.json`) and asks first. **Export…** writes a `.sanduhrpack` where you choose: the kept mod's files, its name, version and description, and what Check found; never a folder, path, session or setting. **Open Pack…** (or a double-click on one) reads a pack you choose, unpacks it into a temporary folder that is deleted afterwards, and stages its mod under `mods/.proposed/` exactly as a proposal; `mod-proposals.json` never lists it, so Claude doesn't learn of it. **Export Config…** on By Seat (for a folder marked work too, its pack stamped `"from": "work"` so opening it elsewhere warns) reads that folder's files and writes one `.sanduhrpack` where you choose, holding only the rows you checked: files with your home folder written as `~`, plugins by marketplace source, MCP servers with every env and header value replaced by a `${NAME}` reference, chosen settings keys and environment variable names without values. Files are scanned for secrets first; a hit leaves the file out. For a folder marked work, `watch-words.json` (owner-only) keeps the names you list per folder; Export Config flags and unchecks a row holding one. It never goes in a pack, a log or the MCP server's files, and its suggestions are read from that folder's rows on this Mac. With **Also for other agents** on, the pack also holds `any-agent/`: the same chosen rows rewritten for other coding agents, built only from what the pack already carries, so it adds no file, value or path that isn't there already. **Open Config Pack…** writes into the folder you pick only what it lacks and you checked: files, settings keys, and environment variable values you type (written into that folder's `settings.json`, never into Sanduhr's records). `imports.json` (owner-only) records each import's paths, settings key names and env names with hashes of what was written, never a value, so **Undo Import** can take it back. Plugins and MCP servers you check are put in by Claude Code's own `claude` command, run under that folder's `CLAUDE_CONFIG_DIR` and never while a Claude Code session runs there: `claude plugin marketplace add` and `claude plugin install` download from the marketplace the pack names (a GitHub repo or git URL), and `claude mcp add-json` writes the server, with its `${NAME}` references, into that folder's `.claude.json`. `imports.json` then also records the marketplace, plugin and server names it added. Without `claude`, or for a row you leave unchecked, the commands are only shown. Sanduhr itself sends nothing; what `claude` fetches is Claude Code's own doing. Under the same **Let agents propose mods** switch, Claude can send config for one of your Claude Code folders, named by its folder name, through `propose_config`: files, settings keys and MCP servers with `${NAME}` references, never an env value. Sanduhr checks and scans it again, keeps it owner-only under `mods/.proposed-config/` until you review or dismiss it on By Seat, and `mod-proposals.json` tells the server the folder's name and your decision, never the contents. Reviewing opens it like a config pack: nothing is written until you import, by the same receipts and Undo Import.

No key is ever written to a log.

## What Sanduhr does NOT do

- **No telemetry.** No install pings, no usage analytics, no crash reporting to any server we control.
- **No advertising.** The app displays no ads and sends no data to ad networks.
- **No third-party SDKs** other than the open-source libraries listed in `windows/requirements.txt` (PySide6, cloudscraper, keyring, requests), which run locally and don't make outbound connections beyond what the widget explicitly asks.
- **No account on our side.** You don't sign up with 626Labs. We have no user database. We cannot identify you.

## Who Sanduhr talks to over the network

By default, exactly one destination:

- `https://claude.ai/api/organizations` — to discover which Claude organization your account belongs to
- `https://claude.ai/api/organizations/{your-org-id}/usage` — to read your subscription usage

These are the same endpoints your browser hits when you visit the claude.ai usage page. Sanduhr acts on your behalf using the cookie you paste in — it is not a separate account or identity.

Anthropic's privacy policy governs what they do with those requests: <https://www.anthropic.com/legal/privacy>.

**Only if you set up the Desk's weather piece** (Windows; Settings ▸ Weather, off until you look a city up and place the piece) there is another destination, Open-Meteo:

- `https://geocoding-api.open-meteo.com/v1/search` receives the city name you type when you press Look up, and nothing else.
- `https://api.open-meteo.com/v1/forecast` receives the picked place's coordinates (rounded to about 1 km) and the unit, at most every 30 minutes and only while the Desk shows the piece.

No account, key, cookie, identifier, machine name or app version goes with either request. Open-Meteo's terms: <https://open-meteo.com/en/terms>.

**Only if you turn on Publish usage** (Settings ▸ Publish usage, off by default, and nothing is sent until you also set an endpoint and tick at least one home) there is a second destination, and you choose it:

- The endpoint URL you enter — any absolute http(s) URL you control — receives the daily per-project token counts described in the table above, authenticated the way you configured (bearer token, a header you name, or no credential).
- If you pick the **626 Labs dashboard** preset, that URL is `https://us-central1-project-626labs.cloudfunctions.net/mcp/api/manage_usage`, authenticated with the key you mint in your own dashboard's Agents panel, and the record goes only to *your* dashboard account.

Nothing about your usage comes back to us. The short-version promise above ("does not send your data to 626Labs") holds for every install where this toggle stays off or points anywhere other than the 626 Labs preset, which is every install until you flip it and pick that preset.

## How you remove your data

- **Recommended: Sign Out.** Open Sanduhr → Settings → Credentials → save with an empty `sessionKey` for the account you want cleared. This deletes that account's Windows Credential Manager entries and its local history file.
- **Clear credentials manually:** Windows Start → Credential Manager → delete entries under service `com.626labs.sanduhr`.
- **Clear local storage:** delete `%APPDATA%\Sanduhr\` and `%LOCALAPPDATA%\Sanduhr\`.
- **Uninstall does not wipe credentials.** Start → Apps & features → Sanduhr für Claude → Uninstall removes the installed app files only. It does **not** delete your Windows Credential Manager entries under `com.626labs.sanduhr`, on either the GitHub (.exe) or Microsoft Store install — sign out first, or delete the entries yourself afterward.
- **Note for Microsoft Store installs:** uninstalling from Apps & features does **not** remove `%APPDATA%\Sanduhr` or `%LOCALAPPDATA%\Sanduhr`. From 3.4.3 the Store build writes those two folders at their real paths, so Claude Code, `sanduhr-mcp` and the statusline (which run outside the app package) can read them, and Windows leaves them behind on uninstall like any desktop app's data. To remove them, quit Sanduhr, uninstall it, then delete both folders (paste `%APPDATA%\Sanduhr` and then `%LOCALAPPDATA%\Sanduhr` into File Explorer's address bar). The one-time 3.4.3 upgrade copied older Store data out of the app package; the originals inside the package are removed with the app.
- **On the Mac, Sign Out:** Sanduhr → Settings → Accounts → select the account → Sign Out, then confirm. This deletes that account's `sessionKey` and `cf_clearance` from both the Keychain and the credentials file; signing out the active account also stops fetching and marks `snapshot.json` signed out with no usage figures in it. The account stays in the list, and its usage history (`history.{Account}.json`) and your settings stay.
- **On the Mac, Remove Account:** Settings → Accounts → select the account → Remove Account…, then confirm. This signs it out as above, deletes its history file, and drops it from the list. To remove everything, remove every account (or sign out), delete the folder `~/Library/Application Support/Sanduhr/` and run `defaults delete com.626labs.sanduhr` and `defaults delete com.626labs.sanduhr.desk`.
- **On the Mac, by hand:** delete the `com.626labs.sanduhr` items in Keychain Access (release builds) or the folder `~/Library/Application Support/Sanduhr/` (development builds). Moving the app to the Trash removes neither, so sign out first.
